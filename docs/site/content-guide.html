Content guide - how a module's practice material is built

Workflow for a module

One module, five commands

The loop that keeps solutions, tests, stubs and questions honest.

  1. 1Solution
  2. 2Tests
  3. 3Verify
  4. 4Stubs
  5. 5Check
Pick a step.
study scaffold <module>                # only for brand-new modules (creates templates)
# 1. write solutions/<track>/<NN_module>/exNN_name.py   (docstring = full problem spec)
# 2. write exercises/<track>/<NN_module>/test_exNN_name.py
study verify <module>                  # tests must ALL pass against the solutions
study stubs <module>                   # generates exercise stubs (never overwrites)
pytest exercises/<track>/<NN_module> --no-record   # every test must show as skipped (TODO)
# 3. write questions/<track>/<NN_module>.toml
study check <module>                   # validates; aim for "topics w/o any content: none"

Exercises

File naming: exNN_short_name.py + test_exNN_short_name.py. 4-7 exercises per module, ordered easy -> hard. Each exercise may contain 1-4 functions/classes.

Docstring header (copy this shape exactly - study exercises shows line 2):

"""
Exercise 08.2 - RAG chunker with metadata                       level: ★★☆
topics: generators.rag_chunking, generators.chunk_metadata

Problem
-------
precise spec: signatures, inputs/outputs, edge cases, what must raise what, rules
("don't use X"), so a learner can solve it WITHOUT reading the tests.

Interviewers look for
---------------------
* the concept underneath, the trade-off, the classic bug this exercise guards against

Hints (only after 15 honest minutes)       <- optional
------------------------------------
1. ...
"""

Levels: ★☆☆ fundamentals, ★★☆ working-engineer, ★★★ senior/3-4 YOE interview level. Aim for roughly 1-2 / 2-3 / 1-2 across a module. Prefer realistic, AI-engineering-flavoured scenarios (documents, chunks, embeddings, LLM responses, API clients, configs, logs, eval results) over toy "foo/bar" - but the exercise must still isolate the module's concept.

Good exercise shapes:

  • implement - a function/class with tricky edge cases (LRU cache, retry decorator, rate limiter)
  • fix the bug - solution docstring contains the buggy version in the spec; learner writes the fixed one
  • refactor - make something lazy/thread-safe/typed while keeping behaviour
  • write tests (testing module) - learner writes a test suite; our tests run it against the correct implementation (must pass) and against mutants (must fail)

Solutions: idiomatic, typed, production-quality Python 3.12+ (the venv runs 3.13). They are the learner's reference for "how a senior would write it". Comments explain why, sparingly. Private helpers named _x are dropped from stubs; use __stub_keep__ = ["Name"] for scaffolding (given classes/helpers) that must stay verbatim in the stub.

Tests:

  • import via from study.loader import load; ex = load(__file__, "exNN_name") - never import directly.
  • every test has @pytest.mark.topic("<track>.<module>.<slug>", ...) with full topic ids that exist in curriculum/*.toml (unknown ids abort the run). Tests in one module may also tag topics of other modules when genuinely exercised (e.g. py.decorators.wraps).
  • test behaviour + the concept (laziness, eager validation, no over-consumption, ordering, cancellation, cleanup ran...), not implementation details. Test edge cases.
  • never pytest.raises(Exception) / RuntimeError / BaseException / bare excepts - they'd swallow the stub's NotImplementedError (a subclass of RuntimeError) and pass on unsolved stubs. Use the specific exception, and make a valid call first when testing bad-call errors.
  • tag topics with literal ids ("py.x.y"), never f-strings: study check greps for literals.
  • stubs keep class bodies, constants and signatures verbatim: put answers only inside function bodies, or in _private top-level helpers (dropped from stubs).
  • deterministic & fast: whole module < ~10 s; async timing tests use small sleeps (≤0.2 s) and generous tolerances; seed randomness; no network (use httpx.MockTransport); files via tmp_path.
  • async tests: plain async def test_... (pytest-asyncio auto mode is on).
  • ProcessPoolExecutor: functions defined in exercise modules can't be pickled by child processes (modules are loaded by path); design such exercises so workers are stdlib/builtin callables or keep them thread-based.

One exercise, four views

Real files from py.generators, exercise 08.1. The stub is generated from the solution, never written by hand.

Exercise 08.1 - Lazy log-processing pipeline                     level: ★☆☆
topics: generators.pipelines, generators.lazy_evaluation, generators.chaining

Problem
-------
Build three small generator stages that chain into a pipeline:

    parse(lines)            -> yields dicts {"level": str, "msg": str} from lines like
                               "ERROR  disk full". Skip blank lines and lines starting with "#".
                               Level is the first whitespace-separated word, upper-cased;
                               msg is the rest of the line, stripped.
    only(records, *levels)  -> yields records whose level is in `levels`
    take(n, iterable)       -> yields at most n items, then STOPS pulling from the source

    take(2, only(parse(lines), "ERROR"))

The whole point: the pipeline must be lazy. Pulling 2 errors from a 10 GB log
must only read as many lines as needed to find those 2 errors.

Rules: no lists that hold the whole input. Don't use itertools.islice in `take`
(write it yourself once; use islice in real life).

Interviewers look for
---------------------
* Why pull-based pipelines use O(1) memory regardless of input size.
* That `take` must not call next() one extra time (that would consume an item
  from a shared iterator).

The docstring is the whole problem statement. You can solve the exercise without reading the tests.

from collections.abc import Iterable, Iterator


def parse(lines: Iterable[str]) -> Iterator[dict[str, str]]:
    for line in lines:
        line = line.strip()
        if not line or line.startswith("#"):
            continue
        level, _, msg = line.partition(" ")
        yield {"level": level.upper(), "msg": msg.strip()}


def only(records: Iterable[dict[str, str]], *levels: str) -> Iterator[dict[str, str]]:
    wanted = {lv.upper() for lv in levels}
    return (r for r in records if r["level"] in wanted)


def take(n: int, iterable: Iterable):
    if n <= 0:
        return
    for i, item in enumerate(iterable, 1):
        yield item
        if i >= n:
            return

Idiomatic, typed code you compare with after your own attempt. Private helpers (leading underscore) would be removed from the stub.

Signatures and imports survive, bodies become NotImplementedError. Tests report this as TODO, not as a failure.

class CountingSource:
    """Iterator that records how many items were pulled from it."""

    def __init__(self, items):
        self._it = iter(items)
        self.pulled = 0

    def __iter__(self):
        return self

    def __next__(self):
        item = next(self._it)
        self.pulled += 1
        return item


@pytest.mark.topic("py.generators.lazy_evaluation", "py.generators.memory_efficiency")
def test_pipeline_pulls_minimum():
    src = CountingSource(LINES)
    first_error = list(ex.take(1, ex.only(ex.parse(src), "ERROR")))
    assert first_error == [{"level": "ERROR", "msg": "disk full"}]
    assert src.pulled == 4, "pipeline read more lines than needed"


@pytest.mark.topic("py.generators.exhaustion")
def test_take_does_not_overconsume_shared_iterator():
    it = iter(range(10))
    assert list(ex.take(3, it)) == [0, 1, 2]
    assert next(it) == 3, "take() pulled one item too many"
    assert list(ex.take(0, it)) == []
    assert next(it) == 4

Tests check the concept, here laziness and not over-consuming, and are tagged with the topic ids that update your mastery.

Spot the bad test

An unsolved stub raises NotImplementedError. A good test makes that show as TODO. Which of these tests would give a wrong result on a stub?

def test_rejects_none():
    with pytest.raises(Exception):
        ex.parse(None)
def test_budget_exceeded():
    with pytest.raises(RuntimeError):
        tracker.spend(10**9)
def test_needs_two_args():
    with pytest.raises(TypeError):
        ex.take(1, 2, 3)
def test_take_stops_early():
    it = iter(range(10))
    assert list(ex.take(3, it)) == [0, 1, 2]
    assert next(it) == 3

Question bank (questions/<track>/<NN_module>.toml)

[[q]]
id = "gen-01"            # <short module prefix>-NN, unique in file
topic = "functions"      # topic slug of THIS module (or a full id from another module)
level = 1                # 1 fundamentals | 2 mid | 3 senior (3-4 YOE)
kind = "concept"         # concept | predict | debug | design | compare
q = '''question; may include ```python fenced code```'''
a = '''model answer as bullet points - exactly what a strong candidate says, incl. gotchas'''
followups = ["what the interviewer asks next"]     # optional

Per module: 12-20 questions, about 30% L1 / 45% L2 / 25% L3, with at least 3 predict (show code, ask exact output), 2 debug, and design/compare where meaningful. Answers must be correct - run every predict snippet with the venv Python (and 3.14 if it may differ) and paste the real output. Use ''' for q/a strings that contain """.

Together, exercises + questions should touch every topic in the module (study check).

Python version

The venv runs CPython 3.13; /usr/bin/python3.14 exists separately. Run predict snippets on both when behaviour could differ, and say so in the answer.
