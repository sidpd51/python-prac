Four ideas that come up in almost every AI-engineering interview, as things you can poke. Each one maps to exercises in the Python track.

Lazy pipelines (generators)

A generator pipeline runs when something pulls from the end, and each stage asks the stage before it for one item. That is why memory stays flat on a 50 GB file, and why take(2, ...) must not read one item too many. Practice: study test generators.

Lazy pipelines pull, they don't push

We ask for the first 2 ERROR lines through take(2, only(parse(lines), "ERROR")). Step through and watch how little is read.

    Async concurrency

    Awaiting calls one by one adds their latencies. gather overlaps them, but unbounded fan-out gets you rate-limited, so production code caps in-flight work with a semaphore. Practice: study test async.

    Sequential, gather and semaphore

    Eight embedding calls of different lengths. Pick how they are awaited.

    Retries and backoff

    Retry only what can succeed later (429, 5xx, timeouts), wait longer each time, add jitter, and honour Retry-After. The DocMind HttpEmbedder implements exactly this. Practice: study test http.

    Exponential backoff with full jitter

    Wait is uniform(0, min(max_delay, base × 2^attempt)). The pale bar is the cap, the solid bar is one random draw.

    Without jitter, clients that failed together retry together and hit the API in waves. A numeric Retry-After overrides the formula.

    Identity vs Equality (is vs ==)★★☆ · Python Fundamentals

    CPython 3.14. What does this print?

    a = 256
b = 256
print(a is b)
x = int("257")
y = int("257")
print(x is y, x == y)
s1 = "hello"
s2 = "hel" + "lo"
print(s1 is s2)
t = "".join(["hel", "lo"])
print(s1 is t, s1 == t)
    Answer
    True
False True
True
False True
    • CPython caches small ints -5..256, so every 256 is the same object; 257 built at runtime gives two distinct objects.
    • "hel" + "lo" is constant-folded at compile time to "hello", and identifier-like string literals are interned, so s1 is s2 is True.
    • "".join(...) builds a new string at runtime - equal, not identical.
    • All of this is an implementation detail (it changes between REPL vs file, versions, PyPy). Code that relies on is for ints/strings is a bug; sys.intern() exists if you genuinely need interning (e.g. millions of repeated token strings).
    Mutable vs Immutable Objects★★★ · Python Fundamentals

    What does this print?

    t = ([1], 2)
try:
    t[0] += [3]
except TypeError as e:
    print("TypeError:", e)
print(t)
    Answer
    TypeError: 'tuple' object does not support item assignment
([1, 3], 2)
    • t[0] += [3] is tmp = t[0]; tmp = tmp.__iadd__([3]); t[0] = tmp.
    • list.__iadd__ mutates the list in place (succeeds), then the item assignment back into the tuple fails. So you get an exception and a mutation.
    • Lesson: augmented assignment = in-place operation + rebinding; a tuple only freezes which objects it references, not their contents.
    Dictionary Lookup★★☆ · Python Data Structures

    What does this print?

    from collections import defaultdict
d = defaultdict(list)
print("x" in d, d["x"], "x" in d, len(d))
c = {"a": 1}
print(c.get("b"), c.setdefault("b", []), c)
print(1 in {"a": 1}, "a" in {"a": 1})
try:
    c["zzz"]
except KeyError as e:
    print("KeyError", e)
    Answer
    False [] True 1
None [] {'a': 1, 'b': []}
False True
KeyError 'zzz'
    • Reading a missing key from a defaultdict inserts it (__missing__ calls the factory and stores the result). in and .get() do not.
    • get(k, default) never inserts; setdefault(k, v) inserts if missing and returns the stored value.
    • in on a dict checks keys, not values.
    • d[k] on a plain dict raises KeyError - good when absence is a bug; use .get when absence is expected.
    Dictionaries★★★ · Python Data Structures

    What does this print, and why?

    d = {1: "a", True: "b", 1.0: "c"}
print(d)
s = {0, False, 0.0}
print(s)

    Answer
    {1: 'c'}
{0}
True
    • 1 == True == 1.0 and they hash the same, so they are the same key.

    Variable Scope (LEGB Rule)★★★ · Python Functions

    What does this print, and how do you fix the first one?

    fs = [lambda: i for i in range(3)]
print([f() for f in fs])
gs = [lambda i=i: i for i in range(3)]
print([g() for g in gs])
    Answer
    [2, 2, 2]
[0, 1, 2]
    • Closures capture variables (cells), not values. All three lambdas share the comprehension's single i, looked up when they are called - by then it's 2. ("late binding")
    • lambda i=i: i evaluates the default at creation time, freezing the current value. Alternatives: functools.partial, or a factory def make(i): return lambda: i.
    • Real-world version: creating callbacks/handlers or tool functions in a loop (for name in tools: registry[name] = lambda: run(name)) - every handler runs the last tool.
    Recursion★★★ · Python Functions

    What does this print?

    def flatten(xs, acc=[]):
    for x in xs:
        if isinstance(x, list):
            flatten(x, acc)
        else:
            acc.append(x)
    return acc

print(flatten([1, [2, [3]]]))
print(flatten([4]))
    Answer
    [1, 2, 3]
[1, 2, 3, 4]
    • Passing acc down the recursion is a legit accumulator pattern - but making it a mutable default means the accumulator survives across top-level calls.
    • Fix: acc=None + if acc is None: acc = [], or return new lists (out.extend(flatten(x))), or a generator with yield from flatten(x).
    • Bonus: strings are iterable but must not be recursed into - check isinstance(x, list) (or (list, tuple)), not "is iterable".
    Immutability★★★ · Functional Programming

    What does this print?

    from dataclasses import dataclass, FrozenInstanceError

@dataclass(frozen=True)
class Cfg:
    model: str
    stops: list

c = Cfg("m", ["\n"])
try:
    c.model = "x"
except FrozenInstanceError as e:
    print("frozen:", e)
c.stops.append("END")
print(c)
try:
    hash(c)
except TypeError as e:
    print("TypeError:", e)
    Answer
    frozen: cannot assign to field 'model'
Cfg(model='m', stops=['\n', 'END'])
TypeError: unhashable type: 'list'
    • frozen=True blocks attribute assignment only; the list object inside is still mutable -> shallow immutability.
    • The generated __hash__ hashes the tuple of fields, so a list field makes the instance unhashable at hash time (you'd find out when using it as a cache key).
    • Fix: stops: tuple[str, ...] (and convert in __post_init__ via object.__setattr__(self, "stops", tuple(stops)) if callers pass lists).
    Lazy Evaluation★★★ · Functional Programming

    What does this print?

    x = 10
gen = (x + i for i in range(3))
x = 100
print(list(gen))

xs = [1, 2]
g = (v for v in xs)
xs = [9]
print(list(g))

with open(path) as fh:          # path holds "a\nb\n"
    lines = map(str.strip, fh)
try:
    print(list(lines))
except ValueError as e:
    print("ValueError:", e)
    Answer
    [100, 101, 102]
[1, 2]
ValueError: I/O operation on closed file.
    • In a generator expression only the first iterable (range(3), xs) is evaluated immediately; everything else (x + i) is evaluated lazily when consumed - so it sees x = 100.
    • g captured the original list object; rebinding the name xs later doesn't matter.
    • Lazy iterators over a resource must be consumed while the resource is open - the with block closed the file before list(lines) ran. Materialise inside the block or make the whole pipeline run inside it.
    • General pitfall: lazy code moves errors and side effects to consumption time, far from where the pipeline was built.
    Closures★★☆ · Closures and Scope

    What does this print? How would you fix the first version?

    fns = [lambda: i for i in range(3)]
print([f() for f in fns])
fns = [lambda i=i: i for i in range(3)]
print([f() for f in fns])
    Answer
    [2, 2, 2]
[0, 1, 2]
    • Late binding: all three lambdas close over the same variable i, looked up when they are called - after the loop, i == 2.
    • i=i evaluates the default at definition time, freezing the current value.
    • Cleaner alternatives: a factory function (def make(i): return lambda: i) - each call gets its own cell - or functools.partial(fn, i). The default-arg trick leaks an overridable parameter into the signature.
    Function __code__.co_freevars★★☆ · Closures and Scope

    What does this print?

    def make():
    count = 0
    def inc():
        nonlocal count
        count += 1
        return count
    def get():
        return count
    return inc, get

inc, get = make()
inc(); inc()
inc2, get2 = make()
inc2()
print(get(), get2())
print(inc.__code__.co_freevars, make.__code__.co_cellvars)
print(inc.__closure__[0] is get.__closure__[0], inc.__closure__[0] is inc2.__closure__[0])
    Answer
    2 1
('count',) ('count',)
True False
    • inc and get come from the same make() call, so they share one cell; the second make() call creates a fresh cell.
    • co_freevars (on the inner code object) lists names captured from outside; co_cellvars (on the outer code object) lists locals that inner functions capture.
    • __closure__ is a tuple of cell objects aligned with co_freevars; cell.cell_contents is the current value.
    Multiple Decorators★★☆ · Decorators

    What does this print (in order)?

    def deco(name):
    print("factory", name)
    def wrap(f):
        print("decorating", name, "->", f.__name__)
        def inner(*args, **kwargs):
            print("enter", name)
            return f(*args, **kwargs)
        return inner
    return wrap

@deco("A")
@deco("B")
def hello():
    print("hello")

print("---")
hello()
    Answer
    factory A
factory B
decorating B -> hello
decorating A -> inner
---
enter A
enter B
hello
    • The decorator expressions are evaluated top-down (deco("A") then deco("B")), but they are applied bottom-up: hello = A(B(hello)).
    • At call time the outermost wrapper runs first (onion).
    • A receives a function named inner - because B didn't use functools.wraps.
    Class-based Decorators★★☆ · Decorators

    What happens here?

    class Count:
    def __init__(self, f):
        self.f = f
        self.n = 0
    def __call__(self, *args):
        self.n += 1
        return self.f(*args)

class Agent:
    @Count
    def step(self):
        return "ok"

try:
    Agent().step()
except TypeError as e:
    print("TypeError:", e)
print(Agent.step.n)
    Answer
    TypeError: Agent.step() missing 1 required positional argument: 'self'
1
    • Agent.step is a Count instance, not a function. Functions become bound methods through the descriptor protocol (function.__get__); a plain callable object has no __get__, so Agent().step returns the Count object unchanged and self is never passed.
    • The counter was incremented before the inner call failed.
    • Fix: implement __get__ returning types.MethodType(self, instance) (or functools.partial(self, instance)), or use a function-based decorator.
    One-Pass Iterators★★☆ · Iterators

    What does this print?

    hits = map(str.upper, [])
print(bool(hits))
m = map(str.upper, ["a", "b"])
print(list(m), list(m))
    Answer
    True
['A', 'B'] []
    • Iterator objects don't define __bool__/__len__, so they're always truthy - even if empty. if not results: on a map/filter/generator never detects "no results".
    • map is a one-pass iterator: the second list() gets nothing.
    • Fix: materialize (results = list(...)) if small, or peek with first = next(it, sentinel) and re-attach it with itertools.chain([first], it).
    iter()★★☆ · Iterators

    What does this print?

    it = iter("abcdefg")
print(list(zip(it, it)))
print(list(it))
    Answer
    [('a', 'b'), ('c', 'd'), ('e', 'f')]
[]
    • Both zip arguments are the same iterator, so each tuple takes two consecutive items - the classic "chunk into pairs" idiom (zip(*[iter(xs)] * n)).
    • 'g' is lost: zip pulled it for the first slot, then the second slot hit StopIteration, so the partial tuple is dropped - and 'g' is already consumed. Use zip(..., strict=True) to make length mismatches an error, or itertools.batched (3.12+) to keep the short last chunk.
    Generator Exhaustion★☆☆ · Generators

    What does this print?

    squares = (x * x for x in range(4))
print(sum(squares))
print(sum(squares))
print(list(squares))
    Answer
    14
0
[]

    A generator is a one-pass iterator. The first sum exhausts it; afterwards every consumer sees an empty iterator (no error!). Silent empty results are a classic bug when a generator is passed to two consumers - materialize with list() or recreate it, or use itertools.tee (which buffers).

    Method Resolution Order (MRO)★★☆ · Object-Oriented Programming

    What does this print?

    class Base:
    def setup(self):
        print("Base")

class A(Base):
    def setup(self):
        print("A")
        super().setup()

class B(Base):
    def setup(self):
        print("B")
        super().setup()

class C(A, B):
    def setup(self):
        print("C")
        super().setup()

C().setup()
print([k.__name__ for k in C.__mro__])
    Answer
    C
A
B
Base
['C', 'A', 'B', 'Base', 'object']
    • super() means the next class in the MRO of type(self), not "my parent". Inside A, for a C instance, the next class is B - even though A doesn't know B exists.
    • C3 linearization keeps children before parents and preserves the base order, so Base runs exactly once - that's the point of cooperative multiple inheritance.
    • If A called Base.setup(self) directly, B.setup would be skipped.
    Method Resolution Order (MRO)★★★ · Object-Oriented Programming

    What happens?

    class Base: pass
class A(Base): pass
class X(Base, A): pass
    Answer
    TypeError: Cannot create a consistent method resolution order (MRO) for bases Base, A
    • C3 linearization must keep (1) each class before its parents and (2) the listed base order. X(Base, A) demands Base before A, but A is a subclass of Base, so A must come before Base - contradiction.
    • Fix: list more specific classes first: class X(A, Base) (or just class X(A)).
    • Practical rule: mixins go left, the concrete base class goes right: class SafeClient(RedactMixin, LoggingMixin, BaseClient).
    Multiple Exception Handling★★★ · Exception Handling

    What does this print?

    def run():
    try:
        raise ExceptionGroup("batch", [ValueError("a"), TypeError("b"), ValueError("c")])
    except* ValueError as eg:
        print("values:", [str(e) for e in eg.exceptions])
    except* TypeError as eg:
        print("types:", [str(e) for e in eg.exceptions])
    print("after")

run()
try:
    try:
        raise ExceptionGroup("batch", [ValueError("a"), KeyError("k")])
    except* ValueError:
        print("handled ValueError")
except ExceptionGroup as rest:
    print("left:", rest.exceptions)
    Answer
    values: ['a', 'c']
types: ['b']
after
handled ValueError
left: (KeyError('k'),)
    • Unlike except, every matching except* clause runs, each receiving a sub-group of the matching leaves (always an ExceptionGroup, even for one leaf).
    • Leaves nobody matched are re-raised automatically as a new ExceptionGroup.
    • return/break/continue are a SyntaxError inside except* (several clauses may run, so "which one returns" would be ambiguous).
    • You meet this with asyncio.TaskGroup: failures come out as an ExceptionGroup, so an except ValueError around it silently stops matching.
    try, except, else, finally★★★ · Exception Handling

    What happens here, and why did CPython design it this way?

    err = None
try:
    1 / 0
except ZeroDivisionError as err:
    pass
print(err)
    Answer
    NameError: name 'err' is not defined
    • At the end of an except ... as name: block Python implicitly does del name - even if the name existed before.
    • Reason: the exception holds its traceback, which holds the frame, which holds the local err -> a reference cycle that would keep every local in the frame alive until the cyclic GC runs (big tensors, open sockets...).
    • If you need it later, assign to another name inside the block: saved = err (and be aware you now keep the frame alive).
    Text vs Binary Files★★☆ · File Handling

    What does this print?

    s = "naïve ☕"
print(len(s), len(s.encode("utf-8")), len(s.encode("utf-16")))
b = s.encode("utf-8")
print(b[:4])
try:
    b[:3].decode("utf-8")

    Answer
    7 10 16
b'na\xc3\xaf'

    (the last line prints na followed by the replacement character U+FFFD)

    • str = code points, bytes = encoded bytes. "ï" is 2 bytes and "☕" 3 bytes in UTF-8; UTF-16 = 2-byte BOM + 2 bytes per BMP char.

    __exit__()★★☆ · Context Managers

    What does this print?

    class Quiet:
    def __enter__(self):
        print("enter")
        return "value"

    def __exit__(self, exc_type, exc, tb):
        print("exit", exc_type.__name__ if exc_type else None)
        return "yes"

def f():
    with Quiet() as q:
        print(q)
        raise ValueError("lost")
    return "after with"

print(f())
    Answer
    enter
value
exit ValueError
after with
    • __exit__ receives (type, value, traceback) of the in-flight exception (or three Nones). A truthy return value suppresses the exception - here the non-empty string "yes" is truthy, so the ValueError silently disappears and execution continues after the with block.
    • Only return True deliberately (like contextlib.suppress). Return None/False to let it propagate - forgetting that and writing return self or return result is a real bug.
    • On success, the return value of __exit__ is ignored.
    __exit__()★★★ · Context Managers

    What does this print? What does it mean for writing __exit__?

    class Flaky:
    def __enter__(self):
        return self
    def __exit__(self, et, e, tb):
        raise OSError("cleanup failed")

try:
    with Flaky():
        raise ValueError("real problem")
except Exception as err:
    print(type(err).__name__, "|", repr(err.__context__))
    Answer
    OSError | ValueError('real problem')
    • An exception raised inside __exit__ replaces the in-flight one. The original is only kept as __context__ (shown as "During handling of the above exception..."). Callers that except ValueError no longer catch it; alerts show the cleanup error.
    • Good __exit__ code: keep cleanup minimal, catch and log cleanup failures when an exception is already propagating (or attach them with add_note), and never let a secondary failure mask the primary one.
    • ExitStack follows the same rules and keeps running the remaining callbacks even if one of them raises.
    __init__.py★★☆ · Python Modules and Packages

    pkg/__init__.py:

    __all__ = ["public"]
def public(): ...
def helper(): ...
def _private(): ...

    pkg2.py (no __all__):

    def helper(): ...

    Dependency Management★★☆ · Python Modules and Packages

    Which of the versions 2.0.5, 2.1.0, 2.1.9, 2.10.0, 3.0.0 satisfy each specifier?

    ~=2.1
~=2.1.0
==2.*
>=2.1,<3
!=2.1.*
    Answer
    ~=2.1       2.1.0  2.1.9  2.10.0
~=2.1.0     2.1.0  2.1.9
==2.*       2.0.5  2.1.0  2.1.9  2.10.0
>=2.1,<3    2.1.0  2.1.9  2.10.0

    • ~= is the "compatible release" operator: ~=2.1 == >=2.1, ==2.*; ~=2.1.0 == >=2.1.0, ==2.1.* - the last given component may grow.

    Static Type Checking★★★ · Python Type Hints

    What happens with Python 3.13, and with Python 3.14?

    def embed(doc: Document) -> list[float]:
    return []

print("defined")

class Document: ...

print(embed.__annotations__)
    Answer
    • 3.13: NameError: name 'Document' is not defined - annotations are evaluated when the def executes, and Document doesn't exist yet. Nothing is printed.
    • 3.14 (PEP 649/749, deferred evaluation): annotations are evaluated lazily on first access, so it prints
    defined
{'doc': <class '__main__.Document'>, 'return': list[float]}
    • Pre-3.14 fixes: quote it (doc: "Document") or from __future__ import annotations (all annotations stored as strings; tools must call typing.get_type_hints() to resolve them - which breaks for names only imported under if TYPE_CHECKING:).
    • 3.14 adds annotationlib.get_annotations(obj, format=Format.FORWARDREF / STRING) for tools that must cope with still-undefined names.
    • Static checkers don't care either way - this is about runtime introspection (pydantic, FastAPI, dataclasses).

    Task Cancellation★★★ · Asynchronous Programming

    What does this print? What problem does shield solve, and what does it NOT do?

    import asyncio

async def commit():
    await asyncio.sleep(0.1)
    print("committed")
    return "ok"

async def main():
    inner = asyncio.create_task(commit())
    try:
        await asyncio.wait_for(asyncio.shield(inner), 0.05)
    except TimeoutError:
        print("timed out; inner cancelled?", inner.cancelled())
    print(await inner)

asyncio.run(main())
    Answer
    timed out; inner cancelled? False
committed
ok
    • shield(aw) protects the inner task from cancellation coming from the awaiter: the timeout cancels the outer shield future, the caller gets TimeoutError, but inner keeps running (e.g. finish writing a payment record / saving the conversation turn).
    • It does NOT make it un-cancellable: inner.cancel() directly still cancels it, and at asyncio.run shutdown it is cancelled with everything else.
    • You must keep a reference to the inner task (otherwise it can be GC'd) and usually await it or hand it to a background set; otherwise its exceptions go unobserved.
    • Overuse is a smell: if many things need shielding, the design probably needs a queue/worker that owns the work.
    asyncio.TaskGroup★★★ · Asynchronous Programming

    What does this print?

    import asyncio

async def fail(msg, delay):
    await asyncio.sleep(delay)
    raise ValueError(msg)

async def slow():
    try:
        await asyncio.sleep(1)
    finally:
        print("slow cleaned up")

async def main():
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(slow())
            tg.create_task(fail("a", 0.01))
            tg.create_task(fail("b", 0.5))
    except* ValueError as eg:
        print([str(e) for e in eg.exceptions])
    except* KeyError:
        print("never")

asyncio.run(main())
    Answer
    slow cleaned up
['a']
    • First failure (a at 10 ms) makes the TaskGroup cancel all other children (slow and b) and wait for them - slow's finally runs before the group exits.
    • b was cancelled before raising, so only a is in the group. Cancellations are not reported as errors; only real exceptions are collected into an ExceptionGroup.
    • except* matches by type inside the group (could run several handlers); the KeyError handler doesn't match. A plain except ValueError would NOT catch an ExceptionGroup.
    • vs gather: gather would have let slow and b keep running. TaskGroup guarantees no child outlives the async with block (structured concurrency, like trio nurseries).

    Exponential Backoff★★☆ · Async HTTP and API Integration

    What does this print?

    def delays(base, cap, retries):
    return [min(cap, base * 2**n) for n in range(retries)]

d = delays(0.5, 8.0, 6)
print(d, sum(d))

    And why would you NOT use these delays as-is in production?

    Answer
    [0.5, 1.0, 2.0, 4.0, 8.0, 8.0] 23.5
    • Capped exponential backoff: doubling per retry, capped at max_delay; worst case ~23.5 s of sleeping for 6 retries - bound it by an overall deadline too.
    • Without jitter, every client that failed at the same moment (e.g. a provider blip) retries at exactly the same instants -> synchronized retry storms (thundering herd).
    • Full jitter: random.uniform(0, min(cap, base * 2**n)); "equal jitter" keeps half fixed; "decorrelated jitter" uses the previous delay. AWS's analysis shows full jitter minimises total work.
    • If the server sends Retry-After, prefer it over your own schedule.
